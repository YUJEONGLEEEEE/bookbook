01기획 배경

문제 정의

독서 기록 앱은 이미 많지만, 대부분 기록 자체가 목적이다. 문제는 기록이 귀찮다는 것보다 계속할 이유가 없다는 것이었다.

  • 리뷰를 길게 쓰라고 하면 부담스러워서 쓰지 않는다
  • 기록을 쌓아도 눈에 보이는 변화가 없으니 금방 그만둔다

해결 방향

문제기획적 해결구현
기록이 부담스럽다리뷰 단위를 “한 줄”로 축소 책한줄 — 별점 + 한 문장 + 읽은 날짜만 입력
계속할 이유가 없다기록이 눈에 보이게 쌓이는 보상 구조 책탑쌓기 — 책한줄을 모아 9단계 책 획득
어떤 책을 읽을지 모른다온보딩에서 취향을 먼저 수집 장르 · 연령대 · 성별 기반 맞춤 추천

사용자 흐름

회원가입 · 로그인  →  취향 선택  →  튜토리얼  →  홈
→ 찾기 → 책 상세 → 내책장 담기 / 책한줄 작성 → 책탑쌓기 · 보상 획득

온보딩에서 취향을 먼저 받는 이유는 첫 진입 시 홈이 비어 보이지 않게 하기 위함이다. 취향 정보가 있어야 첫 화면부터 추천 도서를 채울 수 있다.

담당 범위

디자이너 1명과 2인 팀으로 진행했다. 기획은 함께 했고, iOS 앱은 전 화면 · 전 기능을 단독으로 구현했다.

  • 앱 전체 화면 구현 (온보딩 · 홈 · 검색 · 상세 · 내책장 · 책한줄 · 책탑쌓기 · 마이페이지)
  • 게이미피케이션(책탑쌓기) 보상 구조 설계 및 구현
  • 알라딘 오픈 API 연동 및 응답 정제 (네이버 책 API 종료 후 상세 조회를 알라딘 ItemLookUp으로 이관)
  • CoreData 데이터 모델 설계 및 계정별 데이터 격리
  • 공통 컴포넌트 제작 (커스텀 얼럿 · 토스트 · 로딩 뷰 · 페이지네이션 바)

최종 책은 연출을 다르게

빈 상태(Empty State)를 기획하다

책을 하나도 못 받은 사용자가 책탑 화면에 들어오면 아무것도 없는 화면을 보게 된다. 이게 첫인상이 되면 앱을 다시 열지 않는다. 그래서 0개 상태 전용 화면을 따로 설계했다 — 어두운 오버레이 위에 Lottie 조명 애니메이션과 물음표 책을 띄워, “아직 없다”가 아니라 “곧 채워질 자리”로 읽히게 했다.

04구현 하이라이트

① 전 화면 상태 동기화

문제
같은 책이 홈 · 검색 · 상세 · 내책장 네 곳에 동시에 보인다. 상세에서 마음을 눌렀는데 뒤로 가면 이전 상태 그대로면, 사용자는 저장이 안 된 줄 알고 다시 누른다.
판단
화면마다 갱신 코드를 넣으면 화면이 늘어날 때마다 누락이 생긴다. 상태 변경 지점에서 한 번만 알리고, 관심 있는 화면이 각자 구독하는 구조로 갔다.
func postBookStateChange(name: Notification.Name, isbn13: Int) {
    NotificationCenter.default.post(name: name, object: nil,
                                    userInfo: [BookSyncKey.isbn13: isbn13])
}

CoreData 저장 직후 항상 발행하도록 toggleBookmark · incrementLikeCount · decrementLikeCount 등 변경이 일어나는 모든 함수에 못 박았다. isbn13을 함께 실어 보내 구독 측이 해당 셀만 갱신하게 했다.

결과
어느 화면에서 눌러도 나머지 전 화면에 즉시 반영. 새 화면을 추가해도 구독 한 줄이면 동기화에 편입된다.

② 로딩 스피너가 깜빡이는 문제

문제
요청마다 스피너를 띄웠더니, 캐시가 맞거나 응답이 빠를 때 스피너가 나타났다 즉시 사라지며 화면이 번쩍였다. 오히려 느려 보였다.
판단
스피너의 목적은 “기다리는 중”을 알리는 것인데, 짧은 대기에는 알릴 필요 자체가 없다. 표시를 0.4초 지연시키고, 그 전에 응답이 오면 아예 띄우지 않는다.
private let showDelay: TimeInterval = 0.4
private var pendingShow: DispatchWorkItem?

func hideLoading() {
    loadingCount = max(0, loadingCount - 1)
    guard loadingCount == 0 else { return }
    pendingShow?.cancel()   // 빠른 응답이면 예약 취소 — 스피너 자체를 생략
    dismissOverlay()
}

동시에 여러 요청이 겹치는 화면(홈: 추천 + 랭킹 + 신간)을 위해 loadingCount로 참조 카운팅해 마지막 요청이 끝났을 때만 내린다.

추가 개선
직접 만든 스피너(심볼을 써내려갔다 지우는 애니메이션)가 획을 그리는 도중 사라져 어색했다. finishGracefully로 진행 중인 획을 완성한 뒤 페이드아웃하도록 했다.

③ SwiftUI 심볼 애니메이션이 동작하지 않던 문제

문제
로딩 뷰의 그리기 효과를 SwiftUI .symbolEffect(.drawOn)으로 구현하고 UIHostingController로 올렸는데, 전환이 트리거되지 않고 심볼이 투명하게 렌더됐다.
판단
오버레이로 얹은 호스팅 컨트롤러에서는 상태 변화가 애니메이션으로 이어지지 않는다고 보고 UIKit 네이티브 API로 전환했다.
imageView.addSymbolEffect(.drawOn)   // iOS 26+
// iOS 17~25는 .variableColor 로 폴백
결과
정상 동작. 구버전 대응까지 포함해 iOS 17부터 동일한 로딩 경험을 제공한다.

④ 알라딘 API 응답이 JSON으로 파싱되지 않던 문제

문제
알라딘 API를 Output=JS로 호출하면 응답 끝에 세미콜론과 공백이 붙어 있어 JSONDecoder가 실패한다.
판단
호출부마다 문자열을 잘라내면 API를 추가할 때마다 같은 코드가 반복된다. Alamofire의 DataPreprocessor를 구현해 디코딩 직전 단계에서 한 번만 처리했다.
struct AladinJSPreprocessor: DataPreprocessor {
    func preprocess(_ data: Data) throws -> Data {
        var d = data
        let trim: Set<UInt8> = [0x3B, 0x20, 0x09, 0x0A, 0x0D]  // ; space tab \n \r
        while let last = d.last, trim.contains(last) { d.removeLast() }
        return d
    }
}
결과
호출부 코드는 그대로 두고 파싱 계층에서만 해결. 알라딘 API를 쓰는 4개 엔드포인트가 전부 같은 처리를 공유한다.

⑤ 검색 결과에 읽을 수 없는 책이 섞이는 문제

문제
“수학”을 검색하면 문제집 · 교과서가, 소설을 검색하면 전집 세트와 e-book이 상위에 나온다. 독서 기록 앱에서 담을 수 없거나 담을 이유가 없는 결과다.
판단
기획 요구(“읽고 기록할 수 있는 책만 보이게”)를 API 응답 정제로 해결했다. 카테고리 ID · 카테고리명 키워드 · 제목 정규식 세 가지를 조합해 걸러낸다.
var isSetBook: Bool {
    if BookData.excludedTitleKeywords.contains(where: { title.contains($0) }) { return true }
    return BookData.volumeSetPatterns.contains {
        title.range(of: $0, options: .regularExpression) != nil
    }
}
결과
응답 모델에 filteringExcluded()를 두어, 네트워크 계층을 통과하는 모든 결과가 자동으로 정제된다.

⑥ 한 기기에 여러 계정 — 데이터 격리

문제
백엔드가 없어 모든 데이터가 기기에 저장된다. 계정을 바꿔 로그인했더니 이전 계정의 최근 검색어 · 인기 검색어 · 튜토리얼 노출 여부가 그대로 보였다. UserDefaults를 계정 구분 없이 썼기 때문이다.
판단
키에 계정 UUID를 네임스페이스로 붙이는 단일 진입점을 만들고, 계정별 저장은 반드시 이 함수를 통하도록 규칙화했다.
static func scopedKey(_ base: String) -> String {
    "\(base)_\(currentAccountUUID?.uuidString ?? "guest")"
}

// CoreData는 Account 관계로 분리 — 조회 시 항상 현재 계정을 조건에 포함
request.predicate = NSPredicate(format: "isbn13 == %lld AND account == %@",
                                Int64(isbn13), account)
결과
탈퇴 시 해당 계정의 키와 CoreData만 삭제되고 다른 계정은 보존된다. 서버가 붙더라도 계정 단위 구조가 이미 잡혀 있어 동기화 계층만 얹으면 된다.

06백엔드 부재에 따른 설계 선택

포트폴리오용 데모로, 별도 서버 없이 CoreData 기반 로컬 전용으로 구현했다. 이를 숨기지 않고 범위를 명시하는 쪽을 택했다.

  • 회원가입 · 로그인은 기기 내 로컬 계정. 휴대폰 번호는 형식 검증만 수행 (SMS 인증 · 비밀번호 없음)
  • 모든 데이터는 기기의 CoreData에 저장되어 앱 삭제 · 기기 변경 시 초기화
  • 마음(좋아요) 랭킹은 원래 서버 누적 집계가 전제였으나, 백엔드가 없어 데모 시드 데이터로 표시. 기기 내 카운터 위에 동기화 계층만 얹으면 확장 가능한 구조로 남겨뒀다

실 서비스 확장 시 필요한 작업

  • 휴대폰 번호 SMS(OTP) 인증
  • 서버 / 클라우드 DB + 동기화(CloudKit · Firebase 등)를 통한 기기 간 데이터 이전
  • 전체 사용자 좋아요를 합산한 실시간 랭킹 집계

07회고

10개월간 255개의 커밋으로 기획부터 구현까지 이어간 프로젝트다. 가장 크게 배운 것은 “기능이 동작한다”와 “사용자가 쓸 만하다”는 다르다는 점이었다. 로딩 스피너는 동작했지만 깜빡여서 오히려 느려 보였고, 상태 저장은 정상이었지만 화면 간에 반영되지 않아 사용자에겐 실패로 보였다. 두 문제 모두 기능 결함이 아니라 경험 결함이었고, 이후로는 구현을 마친 뒤 반드시 사용자 관점에서 다시 확인하는 습관을 들였다.
